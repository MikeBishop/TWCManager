# History: chargeRateControl / chargeStopMode

## chargeRateControl (1 TWC, 2 API, 3 TWC>=6A + API<6A)
- Mode 2 added 2021-10-28, Nathan Gardiner: 30f32ba "Update to UI to enable API charge rate control" (settings.html.j2 dropdown, 1/2 only) + e9b628d "add early support for API based charge rate adjustment" (TWCSlave `chargeRateControl == 2`: offer wiringMaxAmps from TWC, API sets the rate). No PR/issue/doc rationale found; commit messages only. Inferred motive: car obeys API rate, not just TWC offer.
- Mode 3 added 2023-05-18, Richard van den Berg (RichieB2B): 6697e54, PR #514 (merged 2023-05-27), fixes issue #510.
  - PR #514: "I was not able to get my TWC gen2 to actually offer < 6A to the car. The API can though. So I introduced a new option: `Use TWC >= 6A + Tesla API < 6A`."
  - Issue #510 (3-phase: 6A = ~4 kW, too coarse for small PV): "The TWC still offers 6A to the car though. It seems to ignore the 1A from the master, 6A seems to be the lowest it will offer" / "TWC will not go lower than 6A even if told to so so via RS485" / "use RS485 for >= 5A and use the API < 5A". Same commit: API amps < 5 must be sent twice (TeslaPy PR 42; dehsgr comment), clamp API amps >= 1 (0 would stop charging).
  - Hardware fact: Gen2 TWC firmware floors the offer at 6A (single TWC, 3-phase car, Model S75D). Unverified for other firmware/Gen3.
- 2025-01-28 ebbe93a: BLE charge-rate support hangs off the same setting ("Settings > Charge Rate Control", docs/modules/Vehicle_TeslaBLE.md:8). "API" now means API-or-BLE.
- 2026-08-05 4fd9c5f / PR #660 (Mike Bishop): in TWC-control mode, raise the car's own limit to max via API/BLE once, because "true charging rate is the minimum of the two" (TWC offer, car limit). Shows the real problem with modes 1/2: a stale limit on the non-preferred side silently caps rate. Implies both channels must be kept coherent, not just "prefer one".
- Today: TWCSlave.py ~L936, ~L1063: `chargeRateControl==2 or (==3 and desiredAmpsOffered<6)` -> APIcontrol: TWC offered wiringMaxAmps, rate queued to vehicle worker. Else TWC controls. MergedEVSE.setTargetPower: 2 -> prefer non-local; else prefer local; falls back to any writable (no mode-3 split there).

## chargeStopMode (1 API stop, 2 stop responding, 3 TWC stop cmd)
- 9dba647 (2019-10-22, Nathan Gardiner) new stopCarsCharging function; d2d0a85 settings UI; 05231bc (2020-04-26) added mode 3 + docs/Settings.md "Stop Charging Method" (pros/cons); c5648c3 (2020-07-28, Mike Bishop) made it int.
- Underlying problem (docs/README.md "Why doesn't charging stop..."): V1 TWCs stop via max amps = 0, "not effective for newer TWC chargers". Car API stop was original answer (2334a2a, Chris Dragon 2018: "Added car API support to allow stop charge on newer TWC firmware"). So API stop exists because Gen2 newer firmware ignores 0 A (min 6A floor, same as above).
- Mode 1 (default): docs: only Tesla cars "at home" via API; non-Tesla "will continue to charge, but at the minimum power per TWC rate". Needs token. Code: cancels pending queued start, queues {"cmd":"charge","charge":False}; after 10 s stopTimeout, Policy.overrideLimit().
- Mode 2: `respondToSlaves=0` for 60 s (TWCMaster.py ~L1920). Docs: ~30 s to stop; works for non-Tesla; "For Tesla vehicles, effective up to three times per charging session" then car refuses until replug; README: can leave car in error state needing unplug/replug. Does not need credentials ("for those not comfortable providing credentials").
- Mode 3: sendStopCommand: RS485 `fc b2` to each slave (fw >= 4.5.3, "disconnecting the relay"). Docs: DIP pos 1 stops Tesla immediately; DIP pos 2 car eventually deems charger broken. "offered primarily for non-Tesla vehicles, not recommended for Tesla."
- startCarsCharging mirrors: 1 -> queue charge True + clearOverride; 2 -> respondToSlaves=1; 3 -> queue charge True.
- MergedEVSE.stopCharging: 1 -> prefer non-local; 2/3 -> prefer local. (Note: stops conflate 3 distinct local mechanisms; Gen3 stop = house_watts=fuse_watts, Controller_Gen3TWCs.md.)

## Would reasons survive "local first, cloud fallback, per-provider suppression"?
- chargeRateControl=1: yes = the default.
- =2 (API *instead of* TWC): no documented case where API is preferred when TWC could do it, except cars/TWCs where the TWC offer is below 6A impossible. Largely subsumed by "TWC when >= 6A". Possible residual: user with a car that ignores TWC reduction -- none found in history. Gap: preferring API for ALL rates was likely just the first implementation of API control.
- =3: the real, evidenced case. Local (Gen2 TWC) cannot offer < 6A, so API/BLE is required below 6A. Under local-first this must become a *capability* (Gen2 min offer 6A; below that, fall through to vehicle provider, with TWC offer pinned at max). Capability must be per-device/firmware (3-phase and Gen3 may differ), not a global mode.
  - Caveat: when the vehicle provider (BLE/API) takes over, the TWC offer must be raised to max and vice versa (#660 min-of-both). Fall-through is not just "try next provider": the two channels are a joint min(), so coherence logic is needed regardless.
  - Caveat: mode 3 is only meaningful if a vehicle channel exists; with none, TWC floor 6A stays (can't go lower; stop instead).
- chargeStopMode=1: becomes "cloud/BLE stop". Under local-first, a local method (BLE stop, or Gen3 0 A) preferred where it exists; Gen2 has no clean local stop at amps=0, so Gen2 falls through to vehicle (BLE/API). Non-Tesla cars: not reachable by vehicle providers; need 2/3.
- =2 and =3 are *not* the same as "local preferred"; they are lossy, car-hostile local fallbacks (3-per-session limit, relay drop, "charger broken" lockout). A user may deliberately choose them only to avoid credentials/cloud or for non-Tesla cars. Best modeled as capability flags on the Gen2 TWC provider (e.g. stop_via_respond_off, stop_via_relay_cmd) used only as last resort when no vehicle channel (non-Tesla or no token/BLE), rather than preferred over a working BLE/API stop. Deliberate "TWC not used for something it can do": none documented; the converse (user avoids API for credential reasons) is documented and is covered by "suppress provider".
- Suppression use-cases with evidence: API calls <5 A need doubling/5 s delay (TeslaPy 42); API 0 A is clamped to 1 A (stop must be a stop command, not set_amps 0); Tesla API rate limits/backoff (e9b628d capped error backoff 10 min). No history found of a user wanting set_amps suppressed specifically; the credentials concern (docs/README.md) is the documented motive for disabling API wholesale.
