### Issues

#### Critical

#### Important

1. **`Vehicle.read()` now runs on the RS-485 serial thread.** TWCManager.py:1569 (RX loop) → `TWCMaster.recordVehicleVIN` → TWCMaster.py:1525 `vehicleIsDefinitelyHome` → TeslaAPI.py:1921 `update_location(0)` → `_readFresh` → `Vehicle.read()`. On a car not believed home, this means up to `commandTimeout` (5 s) of BLE under `_bleLock` for a claimed VIN, plus `is_awake` and `vehicle_data` HTTP requests, all blocking the heartbeat loop. The global constraint says: "`Vehicle.read()` (which may do I/O) is never called from the serial thread". This is a **plan conflict**, not an implementer error: Task 7's plan text says "`vehicleIsDefinitelyHome` exactly as today". The global constraint says the opposite. This task is the first to route the path through `Vehicle.read()`, which is how the conflict surfaced. Main already did this I/O here, and did worse, since its BLE path could wake. Nothing later in the plan removes it. Phase 1 timing: there are no `TeslaBLE` claims until Task 13, so today the cost on this path is two HTTP requests (`is_awake` + `vehicle_data`). Task 13 adds the 5 s BLE timeout under `_bleLock`, so this needs settling before Task 13. Fix (small): make `recordVehicleVIN` call `self.queue_background_task({"cmd": "vehicleIsDefinitelyHome", "vin": slaveTWC.currentVIN})` and dispatch it in the background-task handler next to `checkCharge` (TWCManager.py:~333). Alternatively, the controller records a ruling that this path is an accepted exception until a named later task. Either way it has to be settled before this gate passes, not left open.

#### Minor

1. **TeslaMate cars get new cloud traffic until Task 11** (implementer concern 2/3). Main's telemetry branch did no I/O and returned True. Now `update_location()` (maxAge 0) cascades on every call, and `update_charge()` cascades whenever TeslaMate's `battery_level` is more than 300 s old, which is common for a parked car. When `is_awake()` says online, each cascade is a paid call, at most once per ≥300 s per car: worst case about 288 × $0.002 ≈ $0.58/day/car, against $0 on main. When the car is asleep, both now return False where main returned True. At TeslaAPI.py:1114 (applyChargeLimit, not gated by `ready()`) that means `atHome` is not recomputed from telemetry for a sleeping car. This is inside the accepted "deploy after Task 11" window. **Correction to the report:** concern 2 says Task 11 liveness "will not remove it (maxAge 0 never consults the cache)". That is wrong. `Fields.age` = `now - max(obs.at, liveAt)` (Fields.py:112-114), so with liveAt = now the age is 0, and `read()`'s `age <= maxAge` (Vehicle.py:120) hits the cache at maxAge 0. `_readFresh` then accepts on `age <= maxAge`. Task 11 must make sure this holds for `lat` and `batteryLevel` while TeslaMate is healthy. One thing to watch in the whole-branch review: liveness only applies while the latest observation's source is TeslaMate. Once a `vehicle_data` call lands a `TeslaAPI`-sourced `lat` on a parked car, TeslaMate (which publishes on change) may not displace it, and reads go back to being paid once per deferral window.
2. **(e) An all-None BLE reply falls through to the cloud.** Main treated `loc_data is not None` as success: it set whatever was non-None, set `lastAPIAccessTime`, returned True and fed stale coordinates to `atHome`. The new code returns None (Sources.py:66-69) and pays $0.002 if the car is online. I agree with this choice. The `{}` alternative would return the cached observation, and `_readFresh` would fail it on age anyway, so matching main would take extra plumbing for a worse result (a stale position reported as success). It is rarely reachable: charge already returns None on an empty `chargeState`, and location needs a non-empty `locationState` with no lat/lon. The cost is limited by the deferral. A related case: a non-empty BLE reply that lacks the requested field (e.g. `batteryLevel` omitted at 0% by proto3 JSON) also falls through. Same cost, same limit.
3. **Smaller behavioural edges compared with main.** (i) statusDeferral is active but there is no stored value: now False, main True (reachable only if a successful `vehicle_data` lacked `battery_level`). (ii) `update_vehicle_data` sets `self.lat` and then fails on a missing `longitude` (TeslaAPI.py:2403-2408): it returns False, but `update_location` reports success because a newer `lat` landed, and `atHome` is computed with the old `lon`. Main returned False. (iii) `vehicleIsDefinitelyHome` on a car whose `is_awake()` reports asleep: `updated` is False, so `atHome` is not forced True. Main could get there through BLE wake or a `vehicle_data` call. The car is charging at that point, so this is rare.
4. **`fetched` compares stamps, not identity.** `obs.at > before.at` (TeslaAPI.py:2336) misses a real read stamped the same as the previous observation, which can happen with a coarse clock (Windows ≈15 ms). `obs is not before` says the same thing without depending on the clock. Related: `obs.at >= start` mixes the registry clock with `time.time()`. These are the same in production but differ under an injected clock.
5. **The residual cost gap the implementer disclosed is confirmed (b).** When `update_vehicle_data` gets a 200 response but `drive_state`, `charge_state` or lat/lon is missing (TeslaAPI.py:2383-2408), it returns False without setting `statusDeferral` or the error time. The next read then pays again, and only the callers' polling rate limits it. This is pre-existing and rare. Add a short deferral on that path when Phase 2 adds read callers.
6. Implementer concern 5 stands: `atHome` is recomputed on cache hits and on the deferral path. `gpsAge` only gates home *seeding* (TeslaAPI.py:675-685), so a stale fix cannot flip a parked-at-home car to away. The effect is the INFO log line on every call while home is unset, and home may be seeded from a cached position with no fix time, as main's telemetry path also did.
